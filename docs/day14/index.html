CH0경계

모델과 하네스의 경계

모델이 하는 일

글을 읽고 다음에 무엇을 할지 고른다.

말할 줄 안다 · 코드를 쓸 줄 안다
파일을 직접 열지는 못한다

하네스가 하는 일

고른 것을 실제로 실행하고 결과를 돌려준다.

파일을 열어 준다 · 명령을 돌려 준다
못 할 일을 막고 · 규칙을 앞에 붙인다

바꿀 수 있는 쪽
모델은 고르는 데까지다. 나머지는 전부 하네스가 하고, 그쪽은 고칠 수 있다.
/
CH0역할

하네스가 맡는 네 가지

1
도구 — 파일 읽기 · 명령 실행 · 검색 · 브라우저를 쥐여 준다. 없으면 말만 한다.
2
순서 — 무엇을 먼저 하고 언제 멈출지 정한다. 계획 → 실행 → 검증 같은 흐름이다.
3
가드레일 — 지우면 안 될 것을 막고, 위험한 명령은 사람에게 물어본다.
4
배경 — 프로젝트 규칙 · 코딩 관례 · 자주 쓰는 절차를 매번 안 적어도 들어가게 한다.
오늘 손대는 곳
넷 다 설정 파일과 문서로 바꾼다. 모델을 바꾸는 것이 아니다.

CH1방법

계획을 세우는 세션과 실행하는 세션

계획은 컨텍스트가 아니라 파일에 남긴다
# 1. 계획 세션 — 코드는 아직 안 건드린다
> 설비 조회 화면을 만들자                ← 계획 모드로 들어간다
● 인수 조건 5개 · 작업 4개로 정리
> 이 계획을 docs/plan-설비조회.md 로 저장해 줘

# 2. 실행 세션 — 새로 열고 계획서만 읽힌다
> docs/plan-설비조회.md 의 1번 작업부터 해 줘
● Read(docs/plan-설비조회.md)          ← 계획이 컨텍스트로 들어온다
● Edit(app/equipment/page.tsx)
● Bash(npm test)
  ↳ 1번 통과 — 계획서에 [x] 로 표시
두 세션으로 나눈다
계획 세션은 정하기만 한다. 실행 세션은 그 파일만 읽고 차례대로 해 나간다.

CH2배포

플러그인과 마켓플레이스

등록은 명령창에서, 고르는 것은 세션 안에서
# 1. 마켓플레이스를 등록한다 — 명령창에서 한다
$ codex plugin marketplace add <사내조직>/<저장소> --ref main
$ codex plugin add 설비도구@<저장소>
$ codex plugin list

# 2. 세션 안에서는 골라서 켠다
> /plugins                          ← 브라우저가 열린다

# 3. 결과는 ~/.codex/config.toml 에 남는다
[plugins."설비도구@사내저장소"]
enabled = true                      ← 이 줄 하나로 붙었다 떨어진다
사내 배포 방식
사내 GitHub 저장소 하나를 마켓플레이스로 걸면 스킬을 사내에만 돌린다.

쪼갠다

> 설비 화면 세 개를 만들어 줘

● Task(목록 화면)      ● Task(상세 화면)      ● Task(설정 화면)
  ↳ 끝                 ↳ 끝                 ↳ 끝

● Read(3개 결과 비교)                 ← 여기서 합친다
● Bash(npm run build)                 ← 합친 뒤 한 번 돌린다
4단계가 제일 어렵다
쪼개기는 쉽다. 합치기에서 대부분 깨진다. 그래서 조각을 겹치지 않게 자른다.

CH5운영

개인이 못 푸는 설정

1
개인 설정 — ~/.codex/config.toml. 각자 고친다. 각자 풀 수도 있다.
2
프로젝트 설정 — 저장소에 같이 넣는다. 팀이 같은 값을 쓴다.
3
관리자 설정 — requirements.toml. 회사가 걸면 개인이 못 푼다.
회사가 거는 쪽 — 관리자 설정으로 못 풀게 못 박는다
# 승인 담당 · 네트워크 정책 · 샌드박스 수준을 회사가 정한다
# 개인 config.toml 이 이것을 이기지 못한다
부탁과 강제의 차이
개인 설정은 부탁이다. 관리자 설정은 강제다. 사내 규정은 강제 쪽에 건다.
