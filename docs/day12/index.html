MCP 가 아닌 것

CH1실제

오가는 말 한 벌

클라이언트 → 서버 : 무엇이 있나
{"method": "tools/list"}

← 서버가 목록을 돌려준다
{"tools": [{"name": "defect_rate",

            "inputSchema": {"machine": "string"}}]}
클라이언트 → 서버 : 하나를 실행한다
{"method": "tools/call",
 "params": {"name": "defect_rate", "arguments": {"machine": "3호기"}}}

← 결과
{"content": [{"type": "text", "text": "3호기 · 불량률 12.0%"}]}
낯익다
어제 만든 도구 설명서와 호출이 그대로다. 형식만 규약을 따른다.

CH1되묻기

실행 중에 사람에게 묻기

Elicitation — 서버가 도중에 확인을 요청한다

서버  잠깐, 이건 되돌릴 수 없다 → 확인을 요청한다

★

CH2주의

붙이기 전에 볼 네 가지

볼 것왜
누가 만들었나서버는 내 컴퓨터에서 도는 프로그램이다. 설치와 같은 무게로 본다

CH2한도

도구가 많아진 뒤

→

→
비슷한 도구가 많으면 모델이 엉뚱한 것을 고른다. 어제 본 「도구는 좁게」가 여기서도 같다.
★
필요한 서버만 켠다. 앱에 따라서는 필요할 때만 목록을 가져오는 방식을 쓴다.
현실
붙일 수 있다고 다 붙이지 않는다. 안 쓰는 서버는 끈다.

mcp.run()

CH4경계

서버 쪽으로 옮겨 오는 경계

어제 노트북에서MCP 서버에서
OPEN / SHUT 컬럼 목록그대로. 서버 코드 안에 둔다
LIMIT 100그대로. 인자로 받아도 서버가 다시 자른다
읽기 전용 연결그대로. 서버가 쓰는 계정이 조회 전용이다
CALLS 기록더 중요해진다 — 여러 앱이 같은 서버를 부른다
★
경계를 앱에 두면 앱마다 다시 만들어야 한다. 서버에 두면 한 번만 만든다.
이유
서버는 누가 부를지 모른다. 그래서 경계는 부르는 쪽이 아니라 내주는 쪽에 있어야 한다.

오늘 가져갈 다섯 가지

1
규약은 고치는 품을 줄인다. 앱 넷 × 도구 넷이 16개에서 8개가 된다.

서버가 내주는 것은 셋 — Tool · Resource · Prompt. 「누가 부를까」로 가른다.
3
사내 자료를 여는 서버는 stdio 로 시작한다. 밖으로 나갈 일이 없다.
4
모델이 읽는 것은 설명뿐이다. 잘못 불리면 코드가 아니라 설명을 고친다.
